Distributed systems · Desktop software test

Traveler Messaging

Two writers hit a deliberate SQLite write lock. Both retried with their original IDs, and all 20 messages committed exactly once in the desktop test.

November 27, 2026 · Windows desktop prototype for Android phone and Quest 3S messaging.

From shared file to SQLite

  • Individual phone and Quest conversation runs recorded 10 of 10 entries each on the desktop. A scheduled phone run also recorded 10 of 10.
  • A shared-start run recorded 16 of 20. Windows reported file-in-use errors for Phone-E07, Phone-E08, Quest-E03, and Quest-E06.
  • A follow-up simulation recorded 20 of 20 on first attempts. It exercised simultaneous producers under that run’s conditions and left recovery from a failed write open.
  • Desktop-local SQLite tests confirmed that replaying an identical message ID left one record. The intended recipient could acknowledge the message, and repeating the acknowledgment made no further change. Commands on the desktop exercised both the phone and Quest roles.
  • An unauthenticated request to the local gateway was rejected, and nine isolated gateway checks passed. A desktop watcher detected one local message in about 350 ms.

Deliberate lock test

Two producers started together and each sent ten distinct IDs through Traveler’s existing enqueue code. The harness used a fresh Windows SQLite database in WAL mode, held a separate write transaction, and waited for both first sends to report contention. It released the lock after 11.0 seconds and retried each failed send with its original ID. A separate connection then read the committed rows and checked their IDs and contents against the sends.

  • Contention observed. CONT-A-01 and CONT-B-01 both returned SQLITE_BUSY while the lock was held, after about 10.98 seconds each. The configured busy timeout was 10 seconds.
  • Two same-ID retries. Both succeeded on their first retry after release. The test harness supplied those retries.
  • 20 committed records and 20 matching send receipts. Zero missing or extra IDs, duplicates, or mismatches. The two induced lock errors were the only errors reported.

Evidence limits. This was one controlled desktop run. It verified committed rows and send receipts under a deliberately held lock. Crash recovery, physical-device delivery, and Android background operation remain open. Windows and Android appeared in Tailscale device status before the network work was paused. Tailscale stayed paused during this test, and Quest integration remains open.

Court of the Synthetic review

The AI-assisted critical review recommended using the desktop SQLite queue as the sole write path. Each reviewer contributed a distinct check.

  • Grok proposed deliberately contending two ten-message producers and requiring 20 unique committed IDs. The desktop test above executed that check.
  • Claude proposed reporting acceptance after commit and tracking recipient acknowledgment separately. Its follow-up test stops the gateway after commit and before the sender receives a receipt, then retries the same ID.
  • Gemini proposed verifying which physical device originates each message, measuring send-to-acknowledgment timing, and testing Android with the screen locked after foreground delivery is established.

The next desktop test is the commit-before-receipt crash case. After that, the first network milestone is a phone-originated message and a desktop reply, each acknowledged by its intended recipient. The airship concept and wind replay are documented on The Traveler page.
